### Virus with gh or gh student?

```plain
This is a known, generic issue and not anything wrong with gh-student specifically. gh extension install foundation50/gh-student pulls a precompiled Go binary straight from GitHub Releases, and unsigned Go binaries distributed this way get flagged constantly by antivirus heuristics — the exact same thing happens to the official GitHub CLI itself (see cli/cli#2064 and cli/cli#13306, where Windows Defender's ML heuristic tagged gh.exe as Trojan:Script/Wacatac.H!ml). It's a well-documented false-positive pattern for small-distribution, unsigned executables, not an indicator the tool is actually malicious — Defender's ML model is just suspicious of a binary with few downloads and no code-signing certificate.

A few ways to actually get your students unblocked:

Fastest fix for the student in front of you: have them (or their campus IT, if it's a managed machine) add an antivirus exclusion for the extension rather than disabling AV entirely. In Windows Security it's Virus & threat protection → Manage settings → Exclusions → Add an exclusion → Folder, pointed at the gh extensions directory (on Windows that's normally under %APPDATA%\GitHub CLI\extensions\gh-student\ — worth having them confirm the actual path with gh extension list or by searching for gh-student.exe, since it can vary). If it's a school-managed laptop where students can't add exclusions themselves, this needs to go through the campus IT/security team instead — no student-side workaround will get past a centrally-managed AV policy.

Fix it at the source: file an issue on foundation50/classroom50 asking the maintainers to either code-sign the gh-student release binaries or proactively submit each release to Microsoft's Defender false-positive submission portal (and to VirusTotal, so other AV vendors' reputation systems pick it up too). Signed releases mostly make this problem disappear; submitting to Microsoft after each release is the cheaper stopgap maintainers of small Go CLIs typically do.

Sidestep it given your setup: since your students already have per-student Incus containers with Tailscale access for the course, it may be simplest to have them run gh student commands from inside their assigned Linux container over SSH rather than on their local Windows machine — Defender never sees the binary at all in that case, and it's consistent with how the rest of the course infra already works.

I'd lead with the exclusion (or IT ticket) for anyone blocked right now, and open the upstream issue in parallel so this stops recurring for the rest of the class.
```
